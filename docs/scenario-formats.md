# Scenario formats

Callprobe uses three scenario formats, one for each kind of check. Each format has
one consistent schema, but the schemas are Callprobe's own, not an external standard.
They build on two common conventions:

- Tools are described with **OpenAI function-calling JSON Schema**: a `name`, a
  `description`, and a `parameters` object validated as JSON Schema draft 2020-12.
- Account checks accept **OpenAI chat-message traces** as well as a native format.

| Format | Files | Checks | Used by |
|---|---|---|---|
| [Tool-decision suite](#tool-decision-suites) | A directory of four YAML files | Selection, schema, argument values, and abstention for one model reply | `callprobe run`, `validate`, `explain` |
| [Agent scenario suite](#agent-scenario-suites) | One JSON file | A multi-turn call sequence against scripted tool outcomes | `callprobe agent run` |
| [Account-check trace and case](#account-check-traces-and-cases) | JSON files | Whether the agent's report matches its recorded calls | `callprobe audit`, `callprobe audit bench` |

The published results use these files:

- Tool-decision numbers: [`src/callprobe/suites/core`](../src/callprobe/suites/core), the
  bundled core suite.
- The 28 agent scenarios: [`examples/agent-validation/suite.json`](../examples/agent-validation/suite.json).
- Account-check evaluations: the case folders under [`examples/didyoureally`](../examples/didyoureally)
  and the bundled benchmark in [`src/callprobe/didyoureally/benchmark`](../src/callprobe/didyoureally/benchmark).

Most frozen suites are generated by scripts, which are the source of truth. Change the
generator and regenerate instead of editing generated JSON; see
[Generated suites](#generated-suites).

## How strictly each format is checked

| | Unknown fields | Duplicate keys | Other checks before any model call |
|---|---|---|---|
| Tool-decision suite (YAML) | **Ignored** | **Not reported; the last value wins** | Every tool and distractor schema; expected tools exist; expected arguments and checks are legal for the schema (`callprobe validate`) |
| Agent scenario suite (JSON) | Rejected | Rejected | Types; unique IDs and tool names; schemas; expected sequence shape; expected arguments satisfy the schema |
| Account-check trace (JSON) | Ignored | Rejected | Event types, roles, statuses, unique call IDs and tool names, finite numbers |

The tool-decision gap is real: a misspelled field such as `exclude_distractor` is
silently ignored. Run `callprobe validate` and review the suite diff when you edit
YAML by hand.

## Tool-decision suites

A suite is a directory with four YAML files:

```
my-suite/
  suite.yaml        name and version
  tools.yaml        tool bundles the tasks can use
  distractors.yaml  plausible but wrong tools for padding
  tasks.yaml        prompts and expected behavior
```

`callprobe init --from-openapi FILE` and `callprobe init --from tools.json` scaffold
this layout. See [Testing your own tools](own-tools.md) for the workflow.

### `suite.yaml`

<!-- example: decision-suite.yaml -->
```yaml
name: refunds-demo
version: 1
```

`name` labels results and reports. `version` is an integer recorded with every run;
raise it when tasks change meaning. Leaderboards and CI gates also compare a hash of the
suite's contents, so any edit to the files is detected even without a new version.

### `tools.yaml`

Tools are grouped into named bundles. A task sees only its own bundle, plus any
distractors added by `--pad`.

<!-- example: decision-tools.yaml -->
```yaml
bundles:
  support:
    - name: issue_refund
      description: Refund part or all of an order. Amount is in cents.
      parameters:
        type: object
        properties:
          order_id: {type: string, pattern: "^ORD-[0-9]{6}$"}
          amount_cents: {type: integer, minimum: 1}
          reason: {type: string, enum: [damaged, late, other]}
        required: [order_id, amount_cents, reason]
        additionalProperties: false
    - name: get_order_status
      description: Look up the current status of one order.
      parameters:
        type: object
        properties:
          order_id: {type: string, pattern: "^ORD-[0-9]{6}$"}
        required: [order_id]
        additionalProperties: false
```

Each tool needs `name`, `description`, and `parameters`. Names must be unique within a
bundle. Prefer `additionalProperties: false`: otherwise the schema check cannot catch
invented arguments.

### `distractors.yaml`

Distractors are plausible tools that are never the right answer for any task. `--pad N`
adds N of them to the bundle so you can measure how accuracy changes as the toolset grows.

<!-- example: decision-distractors.yaml -->
```yaml
tools:
  - name: update_shipping_address
    description: Change the delivery address of an order that has not shipped.
    parameters:
      type: object
      properties:
        order_id: {type: string}
        address: {type: string}
      required: [order_id, address]
      additionalProperties: false
```

### `tasks.yaml`

<!-- example: decision-tasks.yaml -->
```yaml
tasks:
  - id: args-partial-refund
    category: args
    bundle: support
    messages:
      - role: user
        content: >
          Order ORD-991003 came to $84.50 and one of the two mugs was cracked.
          Refund me for just the broken one.
    expect:
      type: call
      tool: issue_refund
      args: {order_id: ORD-991003, reason: damaged}
      arg_checks:
        - {path: amount_cents, op: eq, value: 4225}
    tags: [arithmetic]

  - id: abstain-address-change
    category: abstain
    bundle: support
    messages:
      - role: user
        content: Please send order ORD-620114 to 12 Elm Street instead.
    expect:
      type: no_call
    # The support bundle cannot change addresses, so the model should say so.
    # Padding must never add the tool that would make a call correct.
    exclude_distractors: [update_shipping_address]
```

| Task field | Required | Meaning |
|---|---|---|
| `id` | Yes | Unique task ID |
| `category` | Yes | `select`, `abstain`, `args`, `depth`, or `sequence`; used for per-category scores |
| `bundle` | Yes | The `tools.yaml` bundle the model sees |
| `messages` | Yes | OpenAI-style chat messages sent as the conversation. Multi-turn tasks include earlier turns. |
| `expect` | Yes | The single correct decision for the next reply (below) |
| `tags` | No | Free-form labels |
| `exclude_distractors` | No | Distractor names that padding must never add to this task |

| `expect` field | Meaning |
|---|---|
| `type` | `call`: exactly one call is expected. `no_call`: the model should reply without calling a tool. |
| `tool` | Required for `call`; must be in the task's bundle |
| `also_acceptable` | Other tools that also count as a correct selection |
| `args` | Exact equality on the listed keys only. Keys may be dotted paths such as `path.order_id`. Unlisted arguments are judged by the schema alone. |
| `arg_checks` | Extra assertions on argument values (below) |

`arg_checks` entries have a dotted `path` (list indices are allowed, as in `items.0.sku`),
an `op`, and for most operators a `value`:

| `op` | Passes when |
|---|---|
| `eq`, `neq` | The value equals, or does not equal, `value` |
| `in` | The value is one of the items in `value` |
| `contains` | `value` is contained in the actual value (a substring or list item) |
| `gte`, `lte` | The value, as a number, is at least or at most `value` |
| `matches` | The whole value matches the regular expression in `value` |
| `exists`, `absent` | The path is present, or missing; no `value` needed |

A reply passes when it selects an acceptable tool, makes exactly one call, validates
against the schema, passes every `args` and `arg_checks` assertion, and is not
truncated. A `no_call` task passes only for a complete reply with no calls; running out
of tokens never counts as abstaining. See
[Findings and methodology](findings.md#why-three-scores-instead-of-one) for how the
scores are reported.

Check a suite before spending tokens:

```bash
callprobe validate --suite my-suite
```

## Agent scenario suites

An agent suite is one JSON file. Each case gives the model a prompt and mock tools. When
the model calls a tool, the runner returns the next scripted outcome for that tool
instead of executing anything, then continues the conversation. After the episode, the
decision check scores the call sequence and the account check compares the final reply
with the recorded outcomes.

<!-- example: agent-suite.json -->
```json
{
  "version": 1,
  "name": "refund-demo",
  "cases": [
    {
      "id": "refund-fails",
      "prompt": "Refund order R-42 for 40 USD. Do not retry failed operations.",
      "tools": [
        {
          "name": "issue_refund",
          "description": "Issue a refund. Amount is in dollars, currency is explicit.",
          "parameters": {
            "type": "object",
            "properties": {
              "order_id": {"type": "string"},
              "amount": {"type": "number"},
              "currency": {"type": "string", "enum": ["USD", "EUR"]}
            },
            "required": ["order_id", "amount", "currency"],
            "additionalProperties": false
          },
          "side_effect": true,
          "outcomes": [{"status": "error", "result": {"error": "payment processor unavailable"}}]
        }
      ],
      "expected": [
        {"type": "call", "tool": "issue_refund", "args": {"order_id": "R-42", "amount": 40, "currency": "USD"}},
        {"type": "no_call"}
      ]
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `version` | Must be `1` |
| `name` | Suite label |
| `cases[].id` | Unique; letters, digits, `_` and `-` only |
| `cases[].prompt` | The user's request |
| `cases[].tools[]` | `name`, `description`, `parameters` (inline JSON Schema), `side_effect` (default `true`), and at least one entry in `outcomes` |
| `outcomes[]` | `{"status": "ok" or "error", "result": anything}`, returned for that tool's valid calls in order |
| `cases[].expected[]` | The expected decision for each model turn, in order: `{"type": "call", "tool": ..., "args": {...}}`, ending with exactly one `{"type": "no_call"}` for the final reply |

How an episode is scored:

- Turn *n* of the model is compared with `expected[n]` using the same rules as a
  tool-decision task: one call per turn, the right tool, a schema-valid call, and
  equality on the listed `args`. Extra turns beyond the expected sequence fail.
- Each valid call to a tool consumes that tool's next outcome. A retry script is a list,
  for example an `error` outcome followed by an `ok` outcome.
- A call with schema-invalid arguments returns an `invalid_arguments` error and does not
  consume an outcome. A call to a tool that isn't listed returns `unknown_tool`. A call
  after the outcomes run out returns `mock_outcomes_exhausted`.
- The account check reads the final reply and flags claims that contradict these
  recorded outcomes, such as reporting the failed refund above as done.

Validation rejects unknown fields, wrong types, duplicate case IDs or tool names,
invalid schemas, `$ref` references, dotted top-level argument names, a sequence that
does not end with one `no_call`, expected calls to unlisted tools, and expected
arguments that fail the tool's schema. `callprobe agent init --out FILE` writes the
12-case refund and receipt pilot as a starting point. See the
[agent workflow guide](agent-workflow.md) for running and comparing suites.

## Account-check traces and cases

`callprobe audit` checks a **trace**: the conversation plus every tool call and its
outcome. You can supply claims yourself, or let a model extract them.

### Traces

The native format lists tools and then events in order:

<!-- example: audit-trace.json -->
```json
{
  "id": "refund-wrong-amount",
  "tools": [
    {"name": "get_order", "side_effect": false},
    {"name": "issue_refund", "side_effect": true}
  ],
  "events": [
    {"type": "message", "role": "user", "content": "Please refund order R-42."},
    {"type": "tool_call", "id": "c1", "tool": "issue_refund",
     "args": {"order_id": "R-42", "amount": 400}, "status": "ok", "result": {"refunded": true}},
    {"type": "message", "role": "assistant", "content": "Done! I refunded $40 for order R-42."}
  ]
}
```

- `tools[]` entries take `name`, plus optional `side_effect` (default `true`),
  `description`, and `parameters`. Read-only tools set `side_effect: false` so they are
  never reported as unmentioned actions.
- `message` events have a `role` of `user`, `assistant`, `system`, `developer`, or `tool`,
  and string `content`.
- `tool_call` events have a unique `id`, the `tool` name, `args`, a `status` of `ok` or
  `error`, and an optional `result`.

A trace can also be an OpenAI chat-message recording, either a list of messages or
`{"messages": [...], "tools": [...]}`. See
[`examples/didyoureally/openai_masked_failure.json`](../examples/didyoureally/openai_masked_failure.json)
and the [trace format details](didyoureally.md#trace-formats), including how tool
errors are recognized.

### Claims

To skip model extraction, pass reviewed claims with `--claims FILE`, a JSON list:

<!-- example: audit-claims.json -->
```json
[
  {
    "text": "I refunded $40 for order R-42",
    "tool": "issue_refund",
    "args": {"order_id": "R-42", "amount": 40}
  }
]
```

- `text` is the statement; `tool` is the tool that should back it, or `null` when no
  tool could have done it.
- `args` holds only details the agent actually stated.
- `message_index` is the event position of the assistant message that made the claim.
  Leave it out when the trace has exactly one non-empty assistant message, as above.
  With an OpenAI-format trace, positions count the converted events: tool results merge
  into their calls, and an assistant turn with only tool calls adds no message event.

```bash
callprobe audit refund-wrong-amount.json --claims claims.json
```

This reports the claim as **contradicted**: the agent said 40 and the call used 400.

### Benchmark cases

Benchmark and evaluation cases bundle a trace with labeled claims and the verdicts the
checker should produce:

<!-- example: audit-case.json -->
```json
{
  "id": "refund-wrong-amount",
  "domain": "support",
  "description": "The agent states a different refund amount than the call used",
  "trace": {
    "id": "refund-wrong-amount",
    "tools": [
      {"name": "get_order", "side_effect": false},
      {"name": "issue_refund", "side_effect": true}
    ],
    "events": [
      {"type": "message", "role": "user", "content": "Please refund order R-42."},
      {"type": "tool_call", "id": "c1", "tool": "issue_refund",
       "args": {"order_id": "R-42", "amount": 400}, "status": "ok", "result": {"refunded": true}},
      {"type": "message", "role": "assistant", "content": "Done! I refunded $40 for order R-42."}
    ]
  },
  "claims": [
    {"text": "I refunded $40 for order R-42", "tool": "issue_refund", "args": {"order_id": "R-42", "amount": 40}}
  ],
  "expected": [{"verdict": "contradicted", "tool": "issue_refund"}]
}
```

`expected` lists every finding with its `verdict` (`backed`, `contradicted`, `phantom`,
`masked_failure`, or `unmentioned`) and `tool`. A case passes only when the findings
match exactly. Run a folder of cases with:

```bash
callprobe audit bench --cases my-cases
```

Add `--llm` to extract claims with a model instead of using the labeled ones.

the YAML examples are written by hand.

## Other formats

Callprobe does not read BFCL test files or OpenTelemetry traces yet. Tool definitions
already follow the OpenAI function-calling shape, so they usually convert directly.
OpenTelemetry GenAI traces are the next planned trace format for account checks.
